Client Initialization & Environment Configuration

The frontend connects to Supabase through the official @supabase/supabase-js SDK. The connection logic is isolated cleanly in src/lib/supabase.js: 

import { createClient } from '@supabase/supabase-js';

const supabaseUrl = import.meta.env.VITE_SUPABASE_URL;
const supabaseAnonKey = import.meta.env.VITE_SUPABASE_ANON_KEY;

// Validates whether the developer/buyer has added credentials
export const isSupabaseConfigured = Boolean(supabaseUrl && supabaseAnonKey);

// Instantiates client with persistent local session storage
export const supabase = isSupabaseConfigured
  ? createClient(supabaseUrl, supabaseAnonKey, {
      auth: {
        persistSession: true,      // Stores auth token in browser localStorage
        autoRefreshToken: true,    // Automatically refreshes expired JWT tokens
      },
    })
  : null;
🔐 Session Persistence (persistSession: true)

Saves the authenticated user's session securely in browser local storage. When a student or kitchen manager refreshes the page or re-opens the PWA app, they stay logged in without re-entering credentials.

🛡️ Graceful Configuration Fallback

If environment variables are missing during initial preview or setup, isSupabaseConfigured returns false. Instead of crashing the React application with a white screen, the app displays a helpful warning guide.

Phone Authentication Bridging Architecture

Students register and log in using their phone number and password. Because Supabase Auth natively issues JWT tokens and sessions against an email-based identity engine, the application employs a deterministic phone-to-synthetic-email bridge (src/lib/auth.js): 

const EMAIL_DOMAIN = 'campusfood.com';

// Strips non-digits so formats like "+251-912-345678" become "251912345678"
export function normalizePhoneNumber(phone) {
  return phone.replace(/[^\d+]/g, '').trim();
}

// Generates synthetic identity: "0912345678@campusfood.com"
export function fakeEmailFromPhone(phone) {
  const normalized = normalizePhoneNumber(phone);
  return `${normalized}@${EMAIL_DOMAIN}`;
}

How the Auth Flow Works:

1
User Inputs Phone & Password: On the login/signup screen (src/pages/AuthPage.jsx), the student enters their campus phone number (e.g. 0912345678).
2
Synthetic Auth Call: AuthContext.jsx converts the phone to 0912345678@campusfood.com and calls supabase.auth.signUp() or supabase.auth.signInWithPassword().
3
Public Profile Provisioning: On signup, ensureProfileRow() automatically upserts a row in public.users linked to the Supabase auth.users.id UUID with the user's phone number.
4
Real-Time Session Listener: supabase.auth.onAuthStateChange detects logins and logouts instantly, loading the student profile and syncing UI permissions.

Relational Schema Architecture (PostgreSQL)

The complete database schema is defined in supabase-schema.sql. It consists of three primary tables connected through foreign keys with cascading rules:

Table 1: public.users (Student & Manager Profiles)

Column Name Data Type Constraints & Description
id uuid Primary Key. References auth.users(id) ON DELETE CASCADE.
phone text Unique, Not Null. The student's normalized mobile phone number.
name text Full student name entered during onboarding.
pickup_point text Check Constraint: CHECK (pickup_point IN ('T22', 'T34')). Designated dorm pickup location.
identity_number text Student ID number on campus registry.
is_manager boolean Default false. When true, grants kitchen manager & dispatch dashboard access.
onboarding_complete boolean Default false. Controls whether student must fill profile before entering dashboard.
subscription_status text Check Constraint: CHECK (subscription_status IN ('expired', 'pending', 'active')).
subscription_end_date timestamptz Timestamp when current 30-day meal pass expires.
last_transaction_ref text Mobile bank transfer reference code (e.g. Telebirr/CBE transaction ID).
receipt_url text Public URL of the uploaded Telebirr or CBE receipt image in Supabase Storage.
payment_rejection_reason text Feedback text if manager rejected proof (e.g. "Invalid reference number").

Table 2: public.menu (Campus Daily Meals)

Column Name Data Type Constraints & Description
id uuid Primary Key. Default: gen_random_uuid().
name text Name of the meal option (e.g., "Special Enjera with Shiro", "Pasta Bolognese").
meal_type text Check Constraint: CHECK (meal_type IN ('Breakfast', 'Lunch', 'Dinner')).
max_servings integer Portion batch limit (e.g. 50, or null for unlimited). Prevents over-ordering.
is_sold_out boolean Default false. Immediate toggle for kitchen staff to close orders when a pot runs out.
created_at timestamptz Default now().

Table 3: public.orders (Student Meal Orders)

Column Name Data Type Constraints & Description
id uuid Primary Key. Default: gen_random_uuid().
user_id uuid Foreign Key. References public.users(id) ON DELETE CASCADE.
menu_id uuid Foreign Key. References public.menu(id) ON DELETE RESTRICT (prevents deleting menu in active orders).
meal_type text Check Constraint: CHECK (meal_type IN ('Breakfast', 'Lunch', 'Dinner')).
order_date date Calendar date of service (e.g. 2026-10-11).
status text Check Constraint: CHECK (status IN ('Pending', 'Packed', 'Arrived', 'Delivered')).
Unique Constraint UNIQUE KEY orders_one_per_user_per_meal_per_day (user_id, meal_type, order_date) — Prevents double ordering.

PostgreSQL Stored Procedures & Logic Functions

Rather than relying solely on client-side React code to enforce operational rules, CampusFood embeds critical business logic directly inside PostgreSQL stored procedures:

1. Security Definer Manager Check: public.is_manager()

create or replace function public.is_manager(check_user_id uuid)
returns boolean
language sql
stable security definer
set search_path = public
as $$
  select exists (
    select 1 from public.users
    where id = check_user_id and is_manager = true
  );
$$;

Purpose: Used across Row-Level Security policies to verify if an authenticated user is an authorized kitchen manager. Because it is marked security definer, it executes safely with elevated rights without exposing the entire table.

2. The Time-Window Guardian: public.can_submit_order()

This is the most critical function in the system. It enforces that a student cannot order outside of authorized operational hours, even if someone attempts direct REST API injection: 

create or replace function public.can_submit_order(
  check_user_id uuid,
  requested_menu_id uuid,
  requested_meal_type text,
  requested_order_date date
)
returns boolean
language sql
stable security definer
set search_path = public
as $$
  with server_clock as (
    -- Converts server time directly to Africa/Addis_Ababa timezone
    select timezone('Africa/Addis_Ababa', now()) as addis_now
  ),
  active_window as (
    select
      case
        -- 07:00 to 08:00 AM (420 to 480 minutes)
        when ((extract(hour from addis_now)::int * 60) + extract(minute from addis_now)::int) >= 7 * 60
          and ((extract(hour from addis_now)::int * 60) + extract(minute from addis_now)::int) < 8 * 60
          then 'Breakfast'
        -- 11:00 AM to 01:00 PM (660 to 780 minutes)
        when ((extract(hour from addis_now)::int * 60) + extract(minute from addis_now)::int) >= 11 * 60
          and ((extract(hour from addis_now)::int * 60) + extract(minute from addis_now)::int) < 13 * 60
          then 'Lunch'
        -- 05:00 to 07:00 PM (1020 to 1140 minutes)
        when ((extract(hour from addis_now)::int * 60) + extract(minute from addis_now)::int) >= 17 * 60
          and ((extract(hour from addis_now)::int * 60) + extract(minute from addis_now)::int) < 19 * 60
          then 'Dinner'
        else null
      end as active_meal_type,
      addis_now::date as service_date
    from server_clock
  )
  select exists (
    select 1
    from public.users u
    join public.menu m on m.id = requested_menu_id
    cross join active_window aw
    where u.id = check_user_id
      and u.subscription_status = 'active'
      and u.subscription_end_date > now()
      and m.meal_type = requested_meal_type
      and aw.active_meal_type = requested_meal_type
      and requested_order_date = aw.service_date
  );
$$;
Why This Is Important For Buyers

It guarantees zero cheating or late orders. A student cannot order lunch at 2:00 PM or breakfast at midnight. The database server rejects any unauthorized insert immediately.

3. Auto Timestamp Trigger: public.set_updated_at()

create or replace function public.set_updated_at()
returns trigger language plpgsql as $$
begin
  new.updated_at = now();
  return new;
end;
$$;

create trigger orders_set_updated_at before update on public.orders
for each row execute function public.set_updated_at();

Row-Level Security (RLS) Policies Breakdown

Row-Level Security (RLS) is enabled on all tables (ALTER TABLE ... ENABLE ROW LEVEL SECURITY). This guarantees multi-tenant security:

Target Table Operation Policy Rule Summary
public.users SELECT Users can only view their own row (auth.uid() = id), OR the viewer is a verified manager (is_manager(auth.uid())).
public.users UPDATE Students can update their own onboarding info; managers can update subscription statuses and rejection notes.
public.menu SELECT Open to all authenticated students and managers (true).
public.menu INSERT / UPDATE / DELETE Restricted strictly to managers (public.is_manager(auth.uid())). Students cannot tamper with menu items.
public.orders SELECT A student can only view their own orders; managers can view all orders across all students.
public.orders INSERT Only permitted if public.can_submit_order(...) returns true (active subscription + valid time window).
public.orders UPDATE / DELETE Only managers can update order status (e.g. from Packed to Arrived).

Frontend Database Query Operations

Here are the exact queries executed by the frontend components:

A. Loading Student Dashboard (Parallel Promise Query)

// In src/pages/StudentDashboardPage.jsx
const [menuResult, orderResult] = await Promise.all([
  supabase
    .from('menu')
    .select('*')
    .eq('meal_type', focusedMeal)
    .order('name'),
  supabase
    .from('orders')
    .select('id, status, menu:menu_id(name)')
    .eq('user_id', profile.id)
    .eq('meal_type', focusedMeal)
    .eq('order_date', mealContext.focusDate)
    .maybeSingle(),
]);

B. Submitting an Order

// In src/pages/StudentDashboardPage.jsx
await supabase.from('orders').insert({
  user_id: profile.id,
  menu_id: food.id,
  meal_type: focusedMeal,
  order_date: mealContext.focusDate,
});

C. Manager Bulk Dispatch Action (Mark Building Arrived)

// In src/pages/ManagerDashboardPage.jsx
await supabase
  .from('orders')
  .update({ status: 'Arrived' })
  .in('id', orderIds); // Updates all orders for Dorm T22 or T34 in one batch

D. Manager Approving 30-Day Subscription

// In src/pages/ManagerDashboardPage.jsx
const nextEndDate = addDays(new Date(), 30).toISOString();

await supabase
  .from('users')
  .update({
    subscription_status: 'active',
    subscription_end_date: nextEndDate,
    payment_rejection_reason: null,
  })
  .eq('id', studentId);

How a Buyer Sets Up the Database in 5 Minutes

1
Create a Supabase Project: Go to supabase.com, create an organization, and create a new project.
2
Run the SQL Script: In the Supabase Dashboard, open the SQL Editor, paste the complete contents of supabase-schema.sql, and click Run. All tables, functions, indexes, and RLS policies will be created automatically.
3
Copy API Keys: Go to Project Settings → API. Copy the Project URL and anon public key.
4
Configure .env: In the application root, create a .env file: 
VITE_SUPABASE_URL=https://your-project-id.supabase.co
VITE_SUPABASE_ANON_KEY=eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
5
Create First Manager Account: Sign up through the app UI with your manager phone number. Then in Supabase Table Editor → users, toggle is_manager to TRUE. You now have full manager administrative access!
